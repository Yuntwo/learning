# 智能体支付漫游指南：当 AI 开始自主购物，传统支付何去何从

> 来源：https://mp.weixin.qq.com/s/mi0RZ3yJhKt8OQ6E3yAw1A
> 记录时间：2026-07-26

---

## 核心观点

这篇文章真正想讲的，不是“AI 能不能买东西”，而是：**当交易的执行者从“人”切换成“智能体”之后，支付系统的设计前提会被整体改写**。

传统支付体系主要为“人类主动发起、低频、相对大额、边界清晰”的交易设计；而智能体支付更像是一个**高频、低额、可编排、可带条件、跨主体、跨地域**的结算问题。于是，支付入口、身份认证、信任建立、钱包权限、协议互通和最终结算，都会一起进入重构期。

---

## 为什么值得看

这篇内容值得看，主要有三个原因：

1. **它把“智能体支付”从概念炒作拉回到交易结构本身。**
   文章没有停留在“AI 帮你买杯子”这种表层案例，而是拆出了更本质的三类关系：人类向智能体支付、智能体向智能体支付、智能体向网络支付。

2. **它指出了传统支付体系的真正不适配点。**
   问题不是“现有支付能不能完成扣款”，而是现有体系很难承接大量微支付、条件触发支付、跨链路协作结算和机器之间的即时清算。

3. **它给出了一条相对完整的基础设施图谱。**
   从可编程钱包、稳定币、链上结算，到 x402、ERC-8004、Agent Commerce Kit、Web Bot Auth，文章把“未来需要哪些模块拼起来”讲得比较系统。

如果你在关注以下主题，这篇文章尤其值得读：

- Agent 商业化
- AI 原生支付 / Agentic Commerce
- 稳定币支付与链上结算
- 可编程钱包与策略控制
- 按调用 / 按抓取 / 按推理计费
- 智能体协作与机器经济

## 关键概念拆解

### 1. 智能体支付（Agentic Payments）

这里的“支付”已经不只是用户点一下按钮完成付款，而是智能体在任务执行过程中，**代表人类或代表自己去完成搜索、决策、协商、购买、调用服务、访问数据与清算**。

也就是说，支付被嵌进了工作流，而不是孤立存在于结账页。

### 2. 3V3Cs

文中引用了一个很有解释力的模型：**3V3Cs**。

- 高速度（high velocity）
- 高交易量（high volume）
- 低价值（low value）
- 附带条件（conditional）
- 可组合（composable）
- 全球化（cosmopolitan）

它描述的是：智能体世界里的大量交易，不会是传统电商那种“单笔、清晰、一次性”的支付，而更像是**许多微小动作不断触发的小额结算**。

### 3. 人类 -> 智能体

这类场景下，智能体是人类购买行为的代理人。

例如：

- 在聊天界面中直接完成选品与下单
- 让智能体监控价格并在满足条件时自动购买
- 让智能体协同机票、酒店、订阅、物流等多个系统完成采购

这意味着“对话界面”会逐步变成新型交易入口。

### 4. 智能体 -> 智能体

这是文章最值得关注的部分之一。

未来一个智能体为了完成任务，可能要向其他智能体购买：

- API 调用次数
- GPU 时间
- 模型推理配额
- 数据查询权限
- 任务执行结果

这类支付往往金额极小、频次极高，传统信用卡通道很难承接。

### 5. 智能体 -> 网络

当网络的主要消费者越来越多地变成智能体，而不是人类浏览器时，网站和 API 也会改变收费方式。

文中把这种模式概括为：**按抓取次数付费（pay-per-crawl）**、按访问次数付费、按查询次数付费。

它本质上是在说：未来网络内容、数据和服务，会更像被机器调用的计量式资源，而不是单纯面向人的广告页面或月订阅产品。

### 6. 可编程钱包

如果支付的发起方变成智能体，钱包就不能再假设“有一个人拿着助记词手动确认”。

于是钱包系统要支持：

- 策略控制
- 支出预算
- 速率限制
- 权限边界
- 多签 / TEE / 审计机制
- 服务器端托管与规则执行

也就是说，钱包要从“人手持密钥的工具”变成“可编程授权系统”。

### 7. x402 与 ERC-8004

文末提出两个值得持续关注的标准：

- **ERC-8004**：更偏向智能体之间的发现、身份与信任层
- **x402**：更偏向智能体之间的即时支付与结算层

可以把它们理解为：

- 一个解决“你是谁、我为什么信你”
- 一个解决“既然我信你，怎么把钱无摩擦地付过去”

## 要点整理

### 一、交易入口正在从网页和 App 转向对话与代理

文章从一个很具体的变化切入：用户已经可以在聊天界面内直接购买商品，省去传统的“跳转详情页 -> 加购物车 -> 进入结账页 -> 填表付款”的流程。

这里最关键的变化不是 UX 更顺，而是：

- 商品发现
- 比较与决策
- 支付执行

这三件原本分散在不同页面与系统里的事情，开始被统一进一个“对话代理”中。

这意味着，未来的交易入口不一定是网页首页，也不一定是 App Tab，而可能是一个默认帮你行动的智能体。

### 二、真正决定支付底座的，不是“是否在线支付”，而是 3V3Cs

文章很清楚地说明了：智能体经济里的支付，不再是传统支付系统最擅长的那种模式。

传统系统最适合的是：

- 交易发起者是人
- 交易频率相对有限
- 单笔金额不太小
- 条件逻辑比较简单
- 地域、主体与清算边界比较清晰

而智能体支付越来越像：

- 持续运行
- 高频触发
- 单次金额极低
- 条件丰富
- 多主体协作
- 跨境天然存在

因此，问题已经不是“信用卡能不能刷”，而是**这套基础设施是不是为这种经济活动而设计的**。

### 三、人类 -> 智能体：短期会先吃掉体验最差、链路最碎的交易环节

文章把这部分分成 2C 与 2B 两类理解，是很有帮助的。

#### 2C 场景

在面向消费者的场景里，智能体更像是：

- 私人购物助手
- 旅行规划助手
- 价格监控助手
- 套餐组合与预订代理

它会先改造那些“用户知道自己想要什么，但不想亲自完成所有步骤”的场景。

#### 2B 场景

在企业采购或跨境采购里，智能体价值更大，因为这里的链路更复杂：

- 供应商比较
- 运费与交期协商
- 预算约束
- 多节点联动
- 跨境支付与结算

文章提到，稳定币在全球小额跨境结算里会更自然，因为许多小商户本来就被传统银行和跨境体系排除在高效率之外。

我的理解是：**人类 -> 智能体不会先从“最酷的自动购物”爆发，而会先从“最省时间、最能减少流程摩擦”的采购任务切进去。**

### 四、智能体 -> 智能体：机器之间的微支付会先重塑 AI 服务市场

这是整篇文章最核心的判断之一。

因为一旦智能体成为可持续工作的执行单元，它就不可能什么都自己做，而一定会外包：

- 向别的模型买推理能力
- 向数据服务买调用额度
- 向算力节点买 GPU 时间
- 向任务执行方买结果

而这些交易有两个鲜明特征：

1. **高频**
2. **微额**

传统信用卡模式下，手续费结构会把这种交易直接“做死”。所以这类场景天然推动：

- 稳定币结算
- 预付信用额度
- 即时任务结算
- 原子支付
- 可验证工作量证明

文章还进一步推演了一个更远的方向：智能体不只雇佣智能体，也可能直接雇佣全球范围的人类工作者。

这会让“劳动力”越来越像被 API 化的供给能力。

### 五、智能体 -> 网络：未来很多内容和接口会从订阅制改成计量制

文章把“按抓取付费”讲得很透。

当越来越多的内容消费者不再是人类，而是智能体爬虫、研究代理、搜索代理、执行代理时，网络就会开始发生两个变化：

1. 网站更在意如何识别“谁在访问我”
2. 网站更在意如何让机器访问变现，而不是只靠广告或包月

于是，未来的网站、内容平台和 API 可能都会出现新的计费方式：

- 按抓取次数
- 按查询次数
- 按文档片段
- 按数据集访问
- 按单次分析结果

文中还特别强调，这种模式不会平均分布到所有网站，而是更可能遵循幂律：

- 高价值内容与高价值数据拥有更强计费意愿
- 长尾网站未必值得自己做这套计量系统
- 中介层可能承担认证、计量、分账和清算

这也是为什么 Cloudflare、x402、Web Bot Auth 这类方向会很重要。

### 六、现在仍然处在非常早期：最大的约束不是想象力，而是现实世界的支付规则

文章最后没有一味乐观，而是明确指出几类约束：

#### 1）支付是强监管行业

只要涉及：

- 身份认证
- 反洗钱
- 支付牌照
- 银行网络
- 卡组织规则
- 企业合规

智能体支付就不可能像普通 SaaS 工具那样“技术可行就快速普及”。

#### 2）多数“智能体”仍是半自主工作流

现在很多产品更像工作流自动化，而不是完全自主的经济主体。

所以短期真正会落地的，往往不是“完全自动购物”，而是：

- 由人类触发
- 由系统自动拆解与执行
- 在一些支付节点采用更细颗粒度的结算方式

#### 3）底层基础设施还在补课

包括：

- 更高吞吐、更低延迟的稳定币底座
- 适合服务器端策略执行的钱包系统
- 更完整的身份、授权与信任框架
- 更适配机器流量的计量与收费协议

也就是说，未来方向相对清晰，但离大规模普及还差若干关键基础设施节点。

### 七、最值得记住的判断：未来不是“AI 接入支付”，而是“支付被重写成机器可编排的系统”

这篇文章给我的最大启发是：

> 真正的变化不是 AI 学会支付，而是支付本身会被重构成智能体原生的协作与结算系统。

过去我们把支付看成一个结账动作；未来更像是：

- 身份验证
- 权限控制
- 条件触发
- 即时清算
- 结果验证
- 多方分账

一起组成一个可编排的执行层。

## 实践印证

虽然当前项目处理的是面向商户与结算的传统支付中后台，而不是“智能体支付”，但它恰好能从反面说明：**真实支付系统从来都不只是一个扣款按钮，而是一整套商户入驻、支付配置、结算开户与合规校验流程。**

### 1. 商户开通本身就是一条复杂链路

在 `apps/pay/src/pay-page/model/merchant/createMerchant.ts` 中，系统需要处理：

- 协议展示与商户类型约束
- 行业信息查询
- 银行信息和支行信息查询
- 商户渠道信息回填
- 表单数据与后端渠道结构映射

这说明现实世界里的支付接入，第一步不是“调用支付接口”，而是**先解决商户主体、渠道、行业、银行账户等准入问题**。

### 2. 支付能力不是一次性接入，而是持续配置

在 `apps/pay/src/api/pay-page/paymentSetting.ts` 中，可以看到系统明确区分了：

- 查询支付设置
- 更新支付设置
- 自动结算开关
- 支付方式开关

这和文章里提到的“支付会变成可编排系统”是相通的。真正的支付产品，核心不是静态 API，而是**持续可配置、可开关、可治理的能力集合**。

### 3. 结算开户是支付系统里不可绕过的一层

在 `apps/pay/src/merchant-financial/features/CreateSettlement/index.tsx` 中，提交结算合同时需要组合：

- 邮寄信息
- 收款账户
- 地址信息
- 银行信息
- 税率信息
- 验证码校验
- 最终合同创建

这再次说明：**钱收进来之后，钱怎么合法、安全、可审计地流出去，同样是支付系统的一部分。**

换句话说，这个项目当前处理的是“人类商户支付体系”的复杂现实；而文章讨论的是“智能体商业体系”即将遇到的下一层复杂性。两者虽然阶段不同，但结构上是连续的：

- 今天要处理商户、配置、结算、验证
- 明天还要再加上智能体身份、策略钱包、机器间结算和信任协议

## 我的总结

如果把这篇文章压缩成一句话，我会这样概括：

**智能体支付不是给 AI 加一个付款按钮，而是在把互联网交易从“人类点击结账”重写为“代理自动协商、调用、计量与清算”的系统。**

短期内，最先落地的不会是最科幻的全自动商业世界，而是那些已经能明确创造价值的场景：

- 对话式购物与采购
- AI 服务之间的微支付
- 数据 / 内容 / 接口的按次访问付费
- 策略控制下的钱包与结算系统

再往后看，真正有决定性的，不会只是某一家模型公司是否能完成购物，而是：

- 身份如何建立
- 智能体如何被授权
- 任务如何被验证
- 价值如何被即时结算
- 系统如何在全球范围内保持开放互通

如果只记住一件事，那就是：

> **未来要被改造的不是“支付界面”，而是交易本身。**
