# RAG Chunk 切分策略工程化拆解

> 来源：https://mp.weixin.qq.com/s/Mry0c5FsE5dNYMPXGOPMKg
> 记录时间：2026-08-04

---

## 核心观点

RAG 里的 chunk 切分不是一个简单参数，而是决定检索上限的基础工程模块：只有把文档结构、语义边界、表格、列表、overlap 和评测方法一起设计，召回效果才会真正提升。

---

## 为什么值得看

很多团队做 RAG 时，会先花大量时间调 Embedding、Rerank 和 Prompt，却把切分阶段当成“默认配置”处理，直接用固定 token 长度切块。文章通过一个很典型的面试追问场景，把问题讲透了：

- 固定长度切分会把完整语义截断
- 表格跨页后容易丢表头
- 列表项脱离前导句后会丢掉否定/限制语义
- overlap 如果没有实验支撑，通常只是拍脑袋
- 没有评测集，就无法判断方案到底有没有变好

如果你在做知识库、FAQ、PDF 检索、合同/条款/说明书问答，这篇内容很适合拿来校正对“切分”这件事的认知。

---

## 关键概念拆解

### 1. 切分决定了检索器到底能看到什么

向量检索并不是直接理解整份文档，而是理解被切出来的 chunk。一个 chunk 一旦语义残缺，它的向量表达也会残缺。后面即便换更强的 Embedding 或更贵的 Rerank，也很难把“丢掉的信息”补回来。

### 2. 好的切分要尽量沿着语义边界而不是长度边界

长度边界适合做最粗粒度的保护，但真正决定可检索性的，是这些边界是否符合文档结构：

- 是否跨章节合并了不该合并的内容
- 是否在句子中间切断
- 是否把列表项从前导语里剥离出来
- 是否把表头和数据拆散
- 是否让关键章节过度碎片化

### 3. overlap 的意义是补边界信息，不是越大越好

Overlap 不是默认加一点就行，而是专门处理“关键信息刚好落在两个 chunk 边界处”的问题。它需要结合实验找平衡点，否则只会徒增存储和检索噪声。

### 4. 评测是切分策略的一部分，不是事后补充

如果没有带标注的测试集和分维度评测，你只能凭感觉说“这版好像更好”。文章强调：切分方案的好坏，必须用 Recall@K、按场景拆分的召回率和 badcase 类型来验证。

## 要点整理

### 1. 固定长度切分为什么问题大

文章给出的 V1 很典型：512 token 一刀切，overlap 50。这个方案最大的问题不是“粗糙”，而是它默认文档结构无关紧要。

但现实里的文档不是连续纯文本，尤其是合同、保险条款、制度说明、技术手册，往往有：

- 章节层级
- 列表条目
- 表格与表头
- 长段落中的限定条件
- 否定、例外、前提等关键修饰

一旦在这些位置乱切，chunk 虽然长度合规，但语义已经坏掉了。

### 2. 句子级切分只解决了一半问题

V2 把切分点从 token 边界换到句号、问号、分号等自然边界，确实能解决“半句话被截断”的问题。但它仍然不理解文档结构，所以还有两个核心短板：

- 一级标题、二级标题和正文仍可能混杂
- 表格和列表这些特殊结构仍会被错误拆散

这说明“自然语言边界”和“文档语义边界”不是一回事。前者只够做局部优化，后者才决定检索质量上限。

### 3. V3 的核心不是更复杂，而是更尊重文档本身

文章里的 V3 可以概括成四个动作：

1. 先识别章节层级，再按章节边界组织内容
2. 对超长章节做递归细切，而不是暴力等长截断
3. 对表格做专项处理，保留表头语义
4. 对列表做专项处理，把前导句和条目一起保留

其中最值得记住的是：

- 同一章节尽量待在同一 chunk
- 跨章节内容不要随意拼接
- 超长章节可以继续细切，但不能丢失路径信息
- 特殊结构不要套用普通文本的切分方法

### 4. 章节识别是复杂文档切分的起点

文章提到的文档层级识别采用多策略融合，因为真实文档的编号方式并不统一，可能同时存在：

- 第三条 / 第一章
- 1. / 1.1 / 1.1.1
- （一）/（二）
- （1）/a)

这对工程实现有两个启发：

- 规则不能只写一种编号模式
- 结构识别最好输出统一层级对象，而不是只做一次正则命中

只有先把“这一段属于哪一层、位于哪条路径”识别出来，后面的 chunk 才能保留上下文。

### 5. 超长章节不能只靠缩小 chunk_size 解决

文章指出，像“保险责任”这种章节动不动就三千字。如果只把 chunk_size 调小，看似更安全，实际上更容易把语义切碎。

更合理的方式是：

- 普通章节和关键章节使用不同的 max_size
- 先尝试按子章节继续拆
- 如果没有更细层级，再按句子边界切
- 切出来后依然保留 section_path

这背后体现的是一个重要原则：**chunk_size 应该跟文档类型和语义密度绑定，而不是全库一个通用默认值。**

### 6. 表格处理是很多 RAG 系统的隐藏短板

文章把表格分成两类：

- 小表格：整体保留
- 大表格：按行切分，但每个 chunk 复制表头

这个设计很重要，因为表格里的数据如果失去表头，模型看到的只是一堆没有字段名和单位的数值。即便检索命中，回答也容易胡编。

对工程实现来说，这意味着：

- 表格应有单独 parser
- 切分时要识别 header rows
- metadata 里最好保留表名、分片编号等信息
- 表格 chunk 与正文 chunk 应该分类型处理

### 7. 列表项不能脱离前导句独立存在

文章给的例子非常有代表性：

“以下情况不在承保范围之内：
（1）核辐射及核污染
（2）战争、军事冲突”

如果把“（1）核辐射及核污染”单独切成一个 chunk，它只剩下一个名词短语，完全失去“不在承保范围”这个关键限定条件。用户问“核辐射赔不赔”，系统就很容易检索到这个条目却答反。

所以列表切分至少要做到：

- 前导句和列表项同 chunk 保留
- 如果列表过长必须继续切，前导句要复制到每个子 chunk

### 8. overlap 要靠实验找，不要凭习惯拍值

文章对 overlap 的处理很工程化：

- 先解释 overlap 解决的到底是什么问题
- 再做 0 / 50 / 100 / 200 / 300 token 的实验对比
- 最后选择 100 token 作为性价比最优点

作者还补了一个细节：在确定重叠区域后，继续对齐到句子结尾，减少 overlap 区域本身的截断问题。

这说明 overlap 最佳实践不是“加一点保险”，而是：

- 先明确问题模型
- 再做区间实验
- 再看收益和成本是否平衡

### 9. metadata 决定了后续系统能不能做溯源和补全

文章设计的 chunk metadata 包括：

- doc_id
- chunk_id
- section_path
- chunk_type
- is_key_clause
- prev_chunk_id / next_chunk_id
- token_count
- page_range

这套设计的意义不止是存信息，而是支持后续能力：

- section_path 用于答案溯源
- is_key_clause 用于检索加权
- prev / next 用于检索命中半截信息时自动扩展上下文
- chunk_type 用于针对表格、列表、正文做差异化处理

换句话说，切分模块不该只产出字符串数组，而应该产出带结构语义的索引单元。

### 10. 切分质量必须通过测试集持续评估

文章给出的评估方法非常务实：

- 200 份文档
- 每份 10 个问题
- 共 2000 个 QA 对
- 用 Recall@5 作为核心指标
- 再按表格类、列表类、超长章节类等维度拆开看

这个方法的价值是，它能明确告诉你：

- 当前方案好不好
- 具体是在哪类场景里不好
- 新改动是不是精确修到了短板

从工程角度看，这比“凭产品反馈修一点、凭经验再试一点”成熟得多。

### 11. 三个容易踩的坑，本质上都和“语义残缺”有关

文章后半段列出的坑，表面不同，本质一致：

- chunk_size 太小：上下文不完整
- 表格表头丢失：字段语义不完整
- 列表项被孤立：限定条件不完整

它们最终都会变成一个共同问题：**chunk 被编码成向量时，表达的信息已经不是用户真正需要召回的那份知识。**

### 12. 前沿方向值得了解，但工程上仍要看成本约束

文章最后提了三个进阶方向：

- Semantic Chunking：用向量相似度变化判断切分点
- Late Chunking：先对长文本整体编码，再在向量层切分
- Dynamic Chunk Size：按语义密度动态设置 chunk 大小

这些方向都很有价值，但文章的态度比较实在：不是哪个更先进就用哪个，而是看吞吐、内存、上线时延和整体成本能否承受。这个判断很工程化，也很值得借鉴。

---

## 我的总结

这篇文章最有价值的地方，不是又讲了一遍“RAG 要做切分”，而是把切分真正拉回工程现场：

- 它不是预处理小细节，而是检索上限的地基
- 它不是单个参数调优，而是一整套结构识别、特殊结构处理、overlap 验证和评测闭环
- 它不能靠经验拍脑袋，而要靠测试集和 badcase 驱动

如果只记住一句话，那就是：**切分模块的职责不是“把文档切开”，而是“尽量把可检索语义完整地交给下游系统”。**
