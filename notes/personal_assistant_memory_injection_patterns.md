# 个人助理里的“用户记忆”通常是怎么进模型上下文的

> 来源：基于用户提问与通用个人助理产品架构经验整理
> 记录时间：2026-08-04

---

## 核心观点

业界的个人助理产品里，**用户记忆 / 用户画像通常会以某种形式进入模型上下文**，但不一定是“把所有内容永久写死在 system prompt”。更常见的做法是：

- 把少量稳定偏好常驻在 system / developer 层
- 把长期记忆存进 memory store，按当前问题相关性检索后再注入
- 把部分画像只留在业务层，用来决定模型、工具、回复风格和检索策略

所以更准确的说法不是“画像是不是塞进了系统提示词”，而是：

> **在调用大模型之前，系统会把和当前任务相关的用户长期信息组织成上下文，再注入到 prompt 或工具结果里。**

---

## 为什么值得看

很多人在理解 AI 助理时，会把“记忆”“画像”“系统提示词”这三个概念直接画等号，进而产生两个误区：

1. 以为只要产品支持记忆，就一定是把所有用户信息都塞进 system prompt
2. 以为只要不在 system prompt 里，就等于模型根本没有用到这些信息

这两个判断都不准确。

真正成熟的个人助理实现，更像是一个“上下文编排系统”：

- 哪些记忆要存下来
- 哪些记忆要在这轮取出
- 取出后放在哪一层
- 哪些信息根本不该直接给模型，只用于上游决策

把这件事想清楚，才能真正理解为什么一个助理看起来“像记得你”，以及为什么不同产品的记忆体验差异会很大。

---

## 关键概念拆解

### 1. 常驻提示：少量稳定偏好会进入高优先级提示层

最朴素、也最容易实现的方案，就是把一些稳定偏好直接写进 system prompt 或 developer prompt，例如：

- 默认使用中文
- 回答风格偏简洁
- 用户是工程师
- 遇到高风险操作要先确认

这一类信息的特点是：

- 变化频率低
- 对很多问题都通用
- 需要在多数场景下稳定生效

所以它们常常被长期挂在高优先级提示层里。

### 2. 检索式记忆：长期记忆通常按相关性取回

更主流的做法不是“把全部记忆都常驻”，而是做一层 memory retrieval：

1. 平时把用户长期信息存到 memory store
2. 用户发来新问题后，先判断与哪些记忆相关
3. 只检索少量高相关记忆
4. 把这些记忆作为当前请求的一部分注入模型

这和知识库检索很像，只不过对象不是外部文档，而是“关于这个用户的长期事实”。

### 3. 用户画像不一定直接喂模型，也可能只用于策略决策

业界里有相当一部分“用户画像”并不会原样进入 prompt，而是用于业务层决策，例如：

- 选哪个模型
- 是否优先走工具调用
- 回复默认长度
- 是否需要先澄清
- 先检索哪些知识源

比如：

- 如果用户是专家，就默认少解释基础概念
- 如果用户是新手，就多给操作步骤
- 如果用户偏好短回答，就控制输出长度

这种情况下，画像是被系统用了，但不是直接以自然语言文本喂给模型。

### 4. 成熟系统一般会把“记忆”分层管理

一个可持续的 memory system，通常至少会分成几类：

- **稳定偏好（profile）**：语言、风格、专业背景、常用工具
- **长期记忆（long-term memory）**：持续中的项目、长期目标、固定协作关系
- **短期工作记忆（working memory）**：当前会话里的任务状态、暂存结论、待办
- **策略约束（policy / preference rules）**：哪些行为需要确认、哪些事情默认不做

这些层不是一回事，所以也不应该用一种方式处理。

### 5. 真实难点不在“塞哪里”，而在“取什么”

大模型产品的工程难点通常不是“system prompt 要不要加一句用户画像”，而是下面几个问题：

- 什么信息值得记
- 什么时候取回
- 取多少条最合适
- 如何避免过期画像误导回答
- 如何避免偏好覆盖当前真实任务需求

一个系统如果只会机械地把所有历史偏好都带上，效果往往并不好。

## 要点整理

### 一、把所有记忆永久塞进 system prompt，是最简单但不够优雅的方案

早期产品或小型应用，经常采用这种方式：

- system 里定义角色
- 再拼上一段“用户偏好 / 用户背景 / 注意事项”

优点是实现简单、行为稳定；缺点也很明显：

- prompt 会越来越长
- 许多信息与当前问题无关
- 画像一旦过时，模型仍然会持续被误导
- 偏好、规则、事实容易混在一起

所以这通常是“能工作”的方案，但不是“最成熟”的方案。

### 二、检索式注入是现在更常见的主流思路

更成熟的个人助理系统会把记忆当成一类可检索数据源。

典型流程是：

1. 先持久化用户长期事实
2. 新请求到来后做 query-based retrieval
3. 按 topic、recency、salience 给记忆排序
4. 只把最相关的几条带入本轮上下文

这样做的好处是：

- token 更省
- 当前回答更聚焦
- 旧画像不容易持续干扰
- 系统更容易审计和调试

所以从效果上看，助理像“记得你”，但实现上往往不是“永远背着所有记忆前进”。

### 三、注入位置并不唯一，system 只是其中一种

业界常见的几种注入方式包括：

1. 直接写进 system / developer prompt
2. 作为单独的 memory message 注入
3. 先通过 memory tool 检索，再把 tool result 给模型
4. 先在业务层消费，只把最终决策结果反映到参数或路由上

因此，问题的关键不是“是不是 system prompt”，而是：

> **记忆有没有在生成答案前，被应用层拿来影响这一轮推理。**

只要影响了本轮推理，它本质上就已经进入了“模型可感知或系统可利用的上下文链路”。

### 四、真正成熟的系统会同时维护“原始记忆”和“记忆摘要”

原始记忆通常是一条条事实，例如：

- 用户偏好中文
- 用户是后端工程师
- 用户最近在做支付稳定性相关工作

但每次都把这些原始事实全部带上，并不高效。

所以很多系统还会维护一个 profile summary，例如：

- 用户偏工程化，偏好中文、结论先行、实用型回答，长期关注稳定性、排障和效率工具。

实践上，常见做法是：

- 常驻一个短 summary
- 再补几条与当前请求最相关的原始记忆

这样能在 token 成本和效果之间取得较好平衡。

### 五、成熟实现会避免“画像绑架回答”

一个常见风险是：用户长期偏好是“简短”，但当前问题其实是复杂架构设计；如果系统机械执行“永远简短”，回答反而会变差。

所以更好的实现方式是把画像表达为：

- 默认偏好
- 常见倾向
- 可被当前任务覆盖

也就是说，画像是默认值，不是铁律。

### 六、从系统设计角度看，memory 是 prompt-building pipeline 的一个输入源

一个典型个人助理的链路通常是：

1. 用户消息进入系统
2. 做意图判断与任务路由
3. 读取 profile summary
4. 检索相关长期记忆
5. 读取外部知识、工具数据或历史任务状态
6. 将这些内容拼装成当前请求上下文
7. 调用大模型生成答案
8. 事后判断本轮是否产生了值得保存的新记忆

所以 memory 更像是“上下文编排流水线里的一个模块”，而不是“某段固定的神秘提示词”。

---

## 我的总结

如果只记住一件事，那就是：

> **业界的个人助理确实会把用户记忆用于大模型交互，但更成熟的做法是“分层存储、按需检索、选择性注入”，而不是把所有用户画像永久写死在 system prompt 里。**

也正因为如此，一个助理是否“显得懂你”，核心往往不在模型本身，而在它前面的 memory system、检索策略和上下文编排能力。
