# Agent 评测：方法论与体系设计

> 来源：https://mp.weixin.qq.com/s/7a2L-GatYYwI6s1uK9mTjA
> 记录时间：2026-08-04

---

## 核心观点

Agent 评测的目标，不是证明某次 Demo 跑通，而是把带有随机性、黑盒性和多步骤级联风险的智能系统，持续收敛成可以发布、可以回归、可以复盘的工程质量体系。

---

## 为什么值得看

这篇文章的价值不在于罗列几个评测指标，而在于把 Agent 评测从“上线前抽几条 case 看感觉”提升成一套完整的质量工程方法：先按 Agent 类型定义评测目标，再围绕指标、数据集、评分器、badcase 归因、优化建议和线上闭环把能力串起来。

如果你正在做客服 Agent、任务执行 Agent、知识问答 Agent、带工具调用的多步 Agent，或者在搭建评测平台、灰度门禁、质量看板，这篇内容很值得系统过一遍。

---

## 关键概念拆解

### 1. Agent 评测不是传统接口测试的放大版

传统软件大多面对相对稳定的输入空间和确定性的执行路径，Agent 则不同：

- 用户输入天然开放，覆盖空间几乎不可穷举
- 模型输出存在随机性，同样输入不保证同样答案
- 多轮会话会积累上下文，错误会跨轮传播
- 工具调用会改写环境状态，导致路径和结果互相影响

所以 Agent 评测不能只看“最后答得对不对”，还要看：

- 有没有调用该调用的工具
- 调用顺序是否正确
- 参数是否构造正确
- 过程是否越权、失真或存在潜在风险
- 同一任务多次运行时是否稳定

### 2. 评测体系要先回答三个问题

一套成熟的 Agent 评测体系，本质上要持续回答三件事：

1. 这个版本现在到底行不行
2. 它是哪里不行
3. 修完之后如何验证真的变好了

这意味着评测平台不能只产出一个总分，而必须能沉淀：

- 可复用的数据集
- 可解释的评分结果
- 可追溯的执行轨迹
- 可归因的 badcase 结果
- 可执行的优化行动项

### 3. 评测对象不只是 Agent，也包括 Skill

当 Agent 越来越多依赖 Skill 去完成查询、调用、生成、执行时，Skill 本身也变成被评测对象。至少要检查四类问题：

- 该不该触发
- 触发后有没有走对流程
- 工具参数和执行结果是否正确
- 遇到异常输入或工具失败时能否优雅降级

## 重点对比表

| 维度 | 对话型 Agent | 任务执行型 Agent | Skill 密集型 Agent | 我的理解 |
|------|--------------|------------------|--------------------|----------|
| 核心目标 | 解决整段会话问题 | 完成明确任务 | 正确触发并执行技能 | 不同形态的“完成”定义完全不同，不能混用一套评分标准 |
| 重点观察层级 | Session + Outcome | Trace + Outcome | Trigger + Tool + Artifact | 对话型更怕“每轮都还行，但整体没解决”；任务型更怕流程中断；Skill 型更怕误触发或错参 |
| 常见风险 | 答非所问、过度承诺、上下文丢失 | 工具漏调、顺序错误、状态未变更 | 错触发、参数错误、产物不可用 | 最终答案对，不代表过程安全 |
| 评分重点 | 任务是否真正解决、策略是否妥当 | 步骤是否闭环、结果是否可验证 | 触发正确率、参数正确率、产物可用性 | 对 Agent 的评测必须拆到过程层 |
| 稳定性重点 | 多轮一致性 | 连续成功率 | 多次调用稳定性 | 生产环境最看重“每次都成功”，不是“总有一次成功” |

## 要点整理

### 1. 先按 Agent 类型建评测框架，不要追求万能指标

文章最重要的提醒之一，是不要试图用一套模板打所有 Agent。

评测底层骨架可以复用，比如：

- 执行测试用例
- 采集 Trace
- 运行评分器
- 生成评测报告
- 做 badcase 归因

但真正决定评测价值的是“评什么”和“怎么判”。

如果系统形态没区分清楚，最后常见的问题是：

- 分数看起来漂亮，但和实际业务体验脱节
- 端到端结果看起来正确，却漏掉过程中的高风险动作
- 版本对比时噪声很大，无法判断改动是否真正带来收益

### 2. 对话 Agent 不能只看单轮回答

对话型 Agent 的难点是：每一轮看起来都还不错，但整段会话可能根本没解决用户问题。

因此评测必须同时覆盖四层：

- Turn：单轮回答质量
- Session：整段会话是否完成目标
- Trace：执行路径是否合理
- Outcome：最终业务结果是否达成

这个视角很重要，因为很多线上问题并不是“明显答错”，而是：

- 没把关键信息追问清楚
- 回答礼貌但没有推动问题解决
- 过程里多次偏航，最后勉强给了一个看似正确的结论

### 3. 指标体系的价值在于驱动持续优化

指标不只是为了打分，更是为了让团队知道“该修哪里”。

文中建议把指标分为三层：

- P0：上线门禁，没过就不能发
- P1：版本对比和工程优化指标
- P2：体验观察和长期改善指标

此外，如果系统 heavily 依赖 Skill，还应该补 Skill 子指标，例如：

- 触发准确率
- 流程执行正确率
- 工具参数正确率
- 最终产物可用率
- 异常降级成功率

我很认同这个思路：没有分层指标，团队往往会把“体验优化问题”和“发布阻断问题”混在一起，最后既拉不齐优先级，也做不出稳定门禁。

### 4. 连续成功率比至少一次成功率更接近生产现实

这是全文里非常工程化的一点。

同一个任务跑 N 次，可以看两种结果：

- 至少一次成功率：只要成功一次，就说明模型能力上限存在
- 连续成功率：每次都成功，才说明系统具备发布稳定性

很多 Demo 型产品只看前者，但真正上线的客服、支付、退款、合规场景，更应该看后者。

因为用户不能接受“你多试两次就好了”。

进一步说，版本对比时还需要：

- 置信区间
- 与基线版本的显著性判断
- 最小可感知变化阈值

也就是不仅要看“提升了多少”，还要看“这是不是超出了随机波动”。

### 5. 评测集不是随机线上抽样，而是设计出来的质量资产

文章明确反对“直接从线上随机采样一点数据就做评测”的做法。

原因很简单：

- 正常路径在线上样本里占比太高
- 真正容易出错的边界条件、对抗样本、高风险路径占比很低
- 只做随机抽样，报告经常会显得很好看，但关键问题根本测不到

更合理的建设路径是：

1. 先做一批高质量 golden set，作为发布门禁与版本回归的基线
2. 再扩展分类采样集、长尾集、对抗集、线上回流集
3. 把 badcase 持续沉淀回评测集，而不是只看一次性分析报告

如果是 Skill 型 Agent，用例设计最好按四个层面组织：

- 该不该触发
- 过程对不对
- 最终产物好不好
- 异常情况下能不能稳住

### 6. 评分要坚持“规则优先，Judge 补语义，人审兜高风险”

文章把评分器分成三层，这个结构非常适合工程落地：

#### 第一层：规则评分

能代码化判断的就优先代码化，例如：

- 是否调用了关键工具
- 是否违反了调用顺序
- 是否缺少关键参数
- 是否命中了禁用动作
- 结果状态是否真的变更

#### 第二层：LLM-as-Judge

Judge 更适合去判断语义和策略维度，例如：

- 解释是否清楚
- 回复策略是否妥当
- 是否存在过度承诺
- 是否忠实引用了证据

但 Judge 必须有：

- 清晰可执行的评分标准
- 输出 reason
- few-shot 边界样本
- 周期性与人工复核对齐
- 偏差治理，避免“同模型互相偏爱”

#### 第三层：人工复核

人工不应该承担日常全量评分，而应该处理：

- 高风险样本
- 低置信样本
- 规则与 Judge 冲突样本
- 新版本、新 Prompt、新工具 Schema 的抽检样本

这套分层筛查思路的本质是：

- 低成本系统先做粗筛
- 高价值样本再做精判
- 真正难判的再交给人

### 7. Badcase 分析的核心，不是列错题，而是稳定归因

很多团队评测的终点停留在“列出失败样本”。

文章强调，真正有价值的是把 badcase 持续追到责任模块和可修复原因。

它给出的思路可以概括成五步：

1. 汇总证据：把输入、回复、Prompt、工具调用、异常、耗时、Trace 都拉齐
2. 范围收敛：先根据“问题现象 × 功能模块”映射表缩小排查范围
3. 分模块诊断：逐个看模块输入输出和关键证据
4. 责任判定：确定主责模块、问题分类和问题枚举
5. 结构化落盘：让结果进入工单、看板和回归集，而不是只存在一次性报告里

我觉得这里最值得借鉴的是“现象层分类”和“责任层定责”分离。

比如“事实性错误”“答非所问”“过度承诺”只是现象；真正主责可能落在检索、规则理解、回复生成、工具执行、Guardrail 等不同模块。

如果这一层不拆开，团队很容易把所有问题都模糊归到“模型不稳定”。

### 8. 优化建议必须生成结构化行动项

评测闭环最容易断的地方，就是“报告已经出了，但没人知道下一步怎么改”。

所以优化建议不能只写：

- 优化 Prompt
- 加强训练
- 提升准确率

而应该直接落成能执行的行动项：

- 问题范围
- 关键证据
- 推荐动作
- owner
- 优先级
- 验收方式
- 回归用例

也就是说，评测平台输出的应该不是一段自然语言总结，而是质量任务对象。

### 9. 评测平台的终点不是报告，而是“反馈生产线”

文章最后一部分讲得很透：真正成熟的评测系统，会把线上失败持续转成研发资产。

至少有三类产物要被稳定生产出来：

- 回归用例
- 根因标签
- 修复建议 / 工单

更完整一点，还应该沉淀：

- 用例库
- Trace 库
- Judge 校准集
- 根因知识库
- 回归集

一旦这些质量资产越积越厚，后续 Agent 版本迭代就不再完全依赖个人经验，而是越来越像一条可复用的工程流水线。

## 实践印证

结合当前项目 `paid_stability` 的代码，我觉得这篇文章里的方法论和实际工程非常贴合。

### 1. 主 Agent 已经具备“可评测对象”的基本骨架

在 `agent/agent.go:34-93`，主 Agent 通过以下模块拼起完整执行链路：

- MCP 工具初始化
- Sandbox 后端初始化
- Skill 初始化与 Handler 注入
- SubAgent 装配
- Fornax Prompt 加载
- deep agent 构建

这意味着项目天然具备多模块协同、工具调用、子 Agent 编排等特征，也就天然需要：

- 工具调用正确率评测
- Skill 触发与流程评测
- Trace 级过程评测
- SubAgent 协作一致性评测

如果只看最终回复，很容易漏掉中间流程已经偏航的情况。

### 2. 模型初始化方式很适合接入启动期评测与门禁

在 `agent/init.go:47-88`，多个模型实例会在启动时预热初始化，包括：

- 通用 chat model
- no thinking model
- personal model
- token model
- low thinking model
- 多个 coding model

这类架构非常适合做两类评测：

1. 启动健康检查：模型配置、凭证、依赖是否有效
2. 版本对比评测：不同模型或不同 thinking 档位在同一任务集上的成功率、稳定性、耗时和成本表现

也就是说，这里不仅能做“能不能跑”的检查，更能做“换模型后值不值得发”的基线比较。

### 3. 知识库与外部依赖是评测里不能忽略的风险源

在 `agent/knowledge/init.go:14-55`，知识检索器和索引器会依赖外部知识库配置完成初始化。

这提醒我们：Agent 评测不能只测模型回答，还要覆盖外部依赖层面的行为，包括：

- 检索是否成功
- 配置失效时是否能快速暴露问题
- 初始化失败时是否能被门禁及时阻断
- 检索质量变化是否会影响最终结论

对知识增强型 Agent 来说，知识召回和模型生成往往要拆开测，否则很难判断问题到底出在“没召回”还是“没用好召回结果”。

## 我的总结

如果用一句话概括这篇文章，我会说：Agent 评测不是给系统打一个分，而是把“随机、黑盒、会级联放大错误”的智能行为拆解成一套可观测、可回归、可定责、可修复的质量工程系统。

真正成熟的团队，不会把评测当成上线前抽样检查，而会把它嵌进整个研发闭环：

- 用 golden set 做门禁
- 用 Trace 看过程
- 用规则 + Judge + 人审分层打分
- 用 badcase 流水线做归因
- 用结构化行动项推进修复
- 再把线上失败沉淀回回归资产

如果只记住一件事，那就是：**Agent 评测的目标不是“证明它能行”，而是“保证它持续可用”。**
