Agent评测体系怎么搭

[小红书正文]
很多团队做 Agent 时，最容易掉进一个坑：

Demo 跑通了，就以为系统“差不多能上”。

但 Agent 真正难的，从来不是把一个 case 跑通，而是把一个带随机性、黑盒决策、多轮上下文、工具调用和状态变化的系统，稳定收敛成“可发布的工程质量”。

这也是我看完这篇 Agent 评测方法论文章后，最大的感受：
Agent 评测不是上线前抽查，而是一整套质量工程体系。

为什么这个问题值得搞懂？

因为传统软件测试面对的，大多是相对确定的输入和执行路径；而 Agent 不一样：

1）同样输入，不一定每次都输出一样
2）多轮对话里，前一轮的小偏差会在后面被放大
3）工具调用会改写系统状态，结果不仅取决于“答得对不对”，还取决于“过程有没有跑偏”
4）有些 case 最终答案看起来没问题，但中间路径已经越界、漏调工具或者带了风险，这种假阳性在生产里迟早会爆

所以，Agent 评测不能只问一句：
“最后答案对吗？”

更应该问：
“它是不是稳定地、正确地、可解释地完成了任务？”

我把这篇文章最值得记住的内容，整理成 5 个重点。

1. 先分清 Agent 类型，再谈评测

这一点非常关键。

很多团队上来就想做一套统一评分标准，但不同 Agent 的“完成任务”含义根本不一样。

比如：

对话型 Agent 关心的是整段会话有没有真正解决问题；
任务执行型 Agent 更关心步骤有没有闭环、状态有没有真的变化；
Skill 密集型 Agent 则要重点看该不该触发、触发后流程对不对、工具参数有没有错、产物能不能用。

如果类型没分清，最后就会出现一种很常见的错觉：
分数很好看，但业务体验并不好。

对照看会更清楚：

对话型 Agent：重点看 Session 和 Outcome
任务执行型 Agent：重点看 Trace 和最终状态
Skill 型 Agent：重点看 Trigger、Tool、Artifact

一句话：
先定义“什么叫完成”，再定义“怎么评”。

2. 对话 Agent 不能只看单轮回答

这个点我很认同。

很多对话系统的问题，不是某一轮明显答错，而是每一轮都“答得还行”，但整段会话最后没有解决用户问题。

所以对话 Agent 的评测，至少要同时看四层：

Turn：单轮回答质量
Session：整段会话是否完成目标
Trace：过程中有没有跑偏
Outcome：最终业务结果有没有达成

这也是为什么很多客服、售后、导购类 Agent 线下看起来不错，线上却总让人不满意。

不是它每句话都错，而是它没有把问题真正闭环。

3. 真正有用的指标，不是为了出分，而是为了驱动修复

文章里提到一个很实用的分层方法：

P0：上线门禁，不达标不能发
P1：版本对比和工程优化指标
P2：体验改善和长期观察指标

这背后的价值在于：
评测不是出一张好看的报表，而是帮助团队分清楚什么是“必须拦截”的问题，什么是“可以持续优化”的问题。

如果系统大量依赖 Skill，还要再补一组 Skill 指标，比如：

是否该触发
触发后流程是否正确
工具参数是否正确
最终产物是否可用
异常时是否能降级

这样团队拿到评测结果后，不会只看到一个总分，而是能直接看出：
到底是触发问题、流程问题、参数问题，还是产物质量问题。

4. 生产里最重要的是“连续成功率”

这篇文章里我最喜欢的一个观点就是：
至少一次成功率，不等于生产可用。

同一个任务跑 N 次，只要成功一次，说明能力上限可能存在；
但只有每次都成功，才说明这个系统具备发布稳定性。

这两者的差别非常大。

Demo 场景常常只看：
“你看，它能做出来。”

但生产环境更关心的是：
“用户每次来，它都能做出来吗？”

尤其在客服、支付、退款、合规这类场景里，没人会接受“多试几次总能成功”。

所以评测报告里，除了成功率，最好还要带上：

置信区间
和基线版本的显著性判断
最小可感知变化阈值

说白了，不只是看差了多少，还要看这点差异是不是超出了统计噪声。

5. 评测闭环的关键，不是列 badcase，而是稳定归因

很多团队其实并不缺 badcase。

真正缺的是：
拿到 badcase 之后，能不能快速知道是哪里出了问题，以及接下来该由谁改、怎么改。

这篇文章把根因定位讲得很清楚，我把它压缩成一个实用流程：

第一步，先把证据拉齐：输入、回复、Prompt、工具调用、异常、耗时、Trace。
第二步，根据“问题现象 × 功能模块”先缩小排查范围。
第三步，再逐个检查候选模块的输入输出。
第四步，做责任判定，确定主责模块和问题类型。
第五步，把结果结构化落盘，进入工单、看板和回归集。

这里有一个特别值得借鉴的点：
要把“问题现象”和“责任模块”分开。

比如“事实性错误”“答非所问”“过度承诺”只是表象；
真正主责可能在检索、规则理解、回复生成、工具执行、风控拦截任何一个地方。

如果不拆开，团队最后很容易把所有问题都模糊地归因成“模型不稳定”。

我自己的一个总结是：

评测平台真正的终点，不是报告，而是把线上失败持续转成研发资产。

也就是说，一条 badcase 最终应该沉淀成这些东西：

回归用例
根因标签
结构化修复建议
Judge 校准样本
后续版本的发布门禁样本

这样质量资产越来越厚，Agent 的迭代才不会一直靠人拍脑袋、靠临时救火。

最后给自己留一个判断方法：

如果你们现在做 Agent 评测，还停留在“跑几条 case 看感觉”“有个总分就算评过”“线上出问题再人工排查”，那离真正的工程化质量体系还有很远。

如果只记住一件事，那就是：
Agent 评测的目标，不是证明它偶尔能行，而是保证它持续可用。
